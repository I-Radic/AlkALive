# Deployment Failure Analysis — Why the Hello World Is Not Pure AlkALive

**Date:** 2026-08-01
**Analyst:** Orchestrator Agent (Wave 0 — Forensic Analysis)
**Mission:** Determine why the deployed "Hello World" is a traditional web page with JS/CSS/DOM rather than a pure AlkaLive WASM binary that renders via WebGPU.

---

## Executive Summary

The deployed "Hello World" is **not a pure AlkALive application**. It is a traditional web application that uses JavaScript, CSS, DOM elements, and a CPU-based software renderer to *simulate* what an AlkALive application would look like. The WASM module (`alkalive_app_bg.wasm`) does contain real AlkALive text-stack code (HarfRust shaping, glyph rasterization), but the entire rendering pipeline, frame loop, input handling, and UI are driven by **application-level JavaScript** — not by the AlkALive runtime or a compiled `.alk` source file.

**Root cause:** The AlkALive toolchain is missing its two most critical pieces: (1) a **compiler** that reads `.alk` source files and emits WASM, and (2) a **concrete WebGPU `Backend` implementation** that the runtime can drive. Without these, the previous agent fell back to hand-writing Rust code in an `alkalive-app` crate that mimics the desired behavior via CPU compositing + Canvas 2D `putImageData`, wrapped in a JavaScript frame loop.

## 2. JavaScript Logic Analysis

### 2.1 `deploy/index.html` — Inline JavaScript (lines 58–143)

The HTML file contains **85 lines of inline JavaScript** in a `<script type="module">` block that:

1. **Imports the WASM module** via `import init, { tick, resize, ... } from './alkalive_app.js'` (line 59–67)
2. **Creates a Canvas 2D context** via `canvas.getContext('2d', { alpha: false })` (line 71)
3. **Runs the frame loop** via `requestAnimationFrame(frame)` (lines 102–134):
   - Calls `tick()` in WASM (renders to a CPU framebuffer)
   - Reads the framebuffer pointer via `get_framebuffer_ptr()`
   - Creates a `Uint8Array` view into WASM memory
   - Creates an `ImageData` object from the framebuffer
   - Draws to canvas via `ctx.putImageData(imageData, 0, 0)` ← **this is the rendering method**
4. **Handles resize** via `window.addEventListener('resize', ...)` (lines 93–99)

**Why it contradicts AlkALive:** The entire frame loop lives in JavaScript. The WASM module does not own the rendering pipeline — it merely produces a pixel buffer that JavaScript copies to the canvas. In a pure AlkALive deployment, the WASM module would own the WebGPU context, create render passes, and submit draw calls directly. The JavaScript shell would only instantiate the module and hand over the canvas.

### 2.2 `deploy/alkalive_app.js` — wasm-bindgen Glue (1,025 lines)

This file is auto-generated by `wasm-bindgen` and contains:
- 83 exported function wrappers (lines 1–1025)
- Memory management glue (`__wbindgen_malloc`, `__wbindgen_free`, etc.)
- String marshalling (`__wbindgen_string_new`, `__wbindgen_string_get`)

**Why it exists:** The `alkalive-app` Rust crate uses `#[wasm_bindgen]` to export 83 functions. This is the standard wasm-bindgen output. However, the **problem** is that these 83 functions are the *entire application API* — `init`, `tick`, `set_color`, `set_glow`, `handle_key_press`, `input_insert_char`, etc. This means the application logic is split between Rust (scene construction) and JavaScript (frame loop, input routing, UI). In a pure AlkALive deployment, the WASM module would export a single `start(canvas)` function and own everything else.

### 2.3 `src/app/page.tsx` — React Application (1,544 lines)

The page served at `localhost:3000` is a **full React application** that:
- Manages 20+ state variables (rotation speed, glow, particles, rainbow, search, replace, stats, etc.)
- Renders 145 DOM elements (control panel, buttons, sliders, inputs, kbd shortcuts, etc.)
- Applies 144 inline CSS styles
- Has 7 event listeners (mousedown, mousemove, mouseup, dblclick, click, keydown, resize)
- Imports the WASM module at runtime via `import(/* webpackIgnore: true */ '/alkalive/alkalive_app.js')`
- Runs the frame loop in JavaScript (calls `tick()`, reads framebuffer, `putImageData`)
- Implements all UI controls (color presets, text presets, sliders, toggles, search, replace, statistics) in React/TypeScript

**Why it contradicts AlkALive:** This is a traditional React web application. The AlkALive WASM module is used as a "rendering library" — not as the application itself. The UI (control panel, HUD, keyboard shortcuts display) is entirely in React/DOM/CSS. In a pure AlkALive deployment, there would be no React, no DOM elements, no CSS — the WASM module would render the UI directly to the canvas via WebGPU.

## 4. Rendering Method Analysis

### 4.1 How the visual output is produced

The rendering pipeline is:

```
User types → JavaScript event handler → WASM input_insert_char()
                                         ↓
                                    WASM updates text buffer
                                         ↓
                                    JavaScript requestAnimationFrame(frame)
                                         ↓
                                    WASM tick() — CPU renders to RGBA framebuffer
                                         ↓
                                    JavaScript reads get_framebuffer_ptr()
                                         ↓
                                    JavaScript creates Uint8Array view
                                         ↓
                                    JavaScript creates ImageData
                                         ↓
                                    JavaScript calls ctx.putImageData() ← Canvas 2D
```

**This is a CPU software renderer using Canvas 2D `putImageData`.** There is:
- ❌ **No WebGPU** — no `navigator.gpu`, no `GPUDevice`, no `GPUCanvasContext`, no render passes
- ❌ **No WebGL** — no `WebGLRenderingContext`, no shaders, no buffers
- ❌ **No GPU draw calls** — the WASM module composites pixels on the CPU and JavaScript copies them to the canvas
- ✅ **Real HarfRust text shaping** — the WASM module does use the real `alkalive-text` crate with HarfRust
- ✅ **Real glyph rasterization** — the vendored rasterizer produces real glyph bitmaps

### 4.2 The `SoftwareRenderer` in `crates/alkalive-app/src/renderer.rs`

```rust
pub struct SoftwareRenderer {
    pub framebuffer: Vec<u8>,  // CPU-side RGBA buffer
    pub width: u32,
    pub height: u32,
    glow_buffer: Vec<u8>,
    // ...
}
```

The `SoftwareRenderer`:
1. Clears the framebuffer to black (CPU loop over pixels)
2. Renders a starfield (CPU pixel plotting)
3. Renders particles (CPU alpha-blended pixel plotting)
4. Composites glyph atlas pixels with color modulation (CPU per-pixel alpha blending)
5. Applies a glow/bloom effect (CPU separable box blur)
6. Exposes the framebuffer pointer for JavaScript to read

**This is entirely CPU-based.** No GPU is involved at any point.

### 4.3 Why this is "fake"

The deployment looks like it renders via AlkALive's GPU runtime, but it actually:
- Uses a **CPU framebuffer** (not a GPU texture)
- Uses **Canvas 2D `putImageData`** (not WebGPU render passes)
- Runs the **frame loop in JavaScript** (not in the WASM module)
- Has **all UI in React/DOM/CSS** (not rendered by AlkALive)

The WASM module is used as a "pixel producer" — not as a GPU runtime. This is the opposite of AlkALive's design goal.

## 5. Compiler / Runtime Gap Analysis

### 5.1 Missing: AlkALive Compiler (`alkalive-compiler` crate)

**Status:** Does not exist. There is no `crates/alkalive-compiler/` directory.

**Evidence:**
- `find . -name "*.alk"` returns zero results — no `.alk` source files exist
- `ls crates/ | grep -i compil` returns nothing
- No `[[bin]]` target in any `Cargo.toml` — there is no CLI to compile `.alk` files
- The `alkalive-app` crate's `lib.rs` explicitly states: "It constructs the Hello World scene directly in Rust (bypassing the not-yet-implemented `.alk` compiler)"

**What's needed:** A compiler crate that:
1. Parses `.alk` source files (lexer + parser → AST)
2. Validates semantics (type checking, ownership, visibility)
3. Lowers AST to a runtime-consumable IR (scene description)
4. Either emits a standalone WASM binary, or links the IR into the `alkalive-runtime` which is then compiled to WASM

### 5.2 Missing: Concrete WebGPU `Backend` Implementation

**Status:** The `Backend` trait exists in `alkalive-render/src/lib.rs:356` but has **zero implementations**.

**Evidence:**
- `rg "impl Backend for" crates/` returns no matches
- `rg "wgpu" crates/*/Cargo.toml` returns no matches — `wgpu` is not a dependency
- The `alkalive-render` crate's doc comment states: "The `Backend`, `RenderLoop`, and `Compositor` traits remain **abstract**: their concrete implementations require WebGPU/host bindings delivered in later waves"

**What's needed:** A `WgpuBackend` struct that:
1. Implements `alkalive_render::Backend` using the `wgpu` crate
2. Acquires a `GPUDevice` and `GPUQueue`
3. Creates render pipelines (shaders)
4. Creates textures and buffers
5. Encodes and submits render passes
6. Works in both native and WASM targets (via `wgpu`'s web backend)

### 5.3 Missing: Concrete `RenderLoop` and `Compositor` Implementations

**Status:** Both traits exist but have zero implementations.

**Evidence:**
- `rg "impl RenderLoop for" crates/` → no matches
- `rg "impl Compositor for" crates/` → no matches

**What's needed:** A retained-mode render loop that:
1. Holds scene-graph state across frames
2. Tracks dirty rectangles
3. Calls the render-graph compiler
4. Drives the backend to encode and submit draw calls
5. Owns the `requestAnimationFrame` loop (from inside WASM, not JS)

### 5.4 Missing: Runtime Bootstrap Wiring

**Status:** The `alkalive-runtime` crate is a **178-line stub** with zero dependencies.

**Evidence:**
- `crates/alkalive-runtime/Cargo.toml` has no `[dependencies]` section
- The `Runtime` struct has only `bootstrap_phase` and `is_ready` fields
- The `FrameLoopDriver` only increments `frame_count` and `elapsed` — it does not call layout, render, or input
- The runtime crate does not reference `alkalive-render`, `alkalive-text`, `alkalive-input`, or any other crate

**What's needed:** The runtime must:
1. Instantiate and wire all subsystems (render backend, text stack, input, layout)
2. Drive the frame loop: `input → layout → render-graph compile → submit → present`
3. Own the `requestAnimationFrame` callback (via a thin JS helper, but the logic in Rust)
4. Handle canvas resize, WebGPU context loss, etc.

### 5.5 Missing: IME Bridge (ADR 023)

**Status:** ADR 023 is documented but **not implemented** in code.

**Evidence:**
- `rg "register_ime_handler" crates/` → no matches
- `rg "hidden_input" crates/` → no matches
- The `DomBridge` trait in `alkalive-dom/src/lib.rs:143` still has the closed 5-verb surface (no IME method)
- The trait doc comment says: "no IME method is exposed (§9.5)"

**What's needed:** Per ADR 023:
1. Add `register_ime_handler` to the `DomBridge` trait
2. Create a hidden `<input>` element in the JS shell
3. Forward `compositionstart`/`compositionupdate`/`compositionend` events to WASM
4. The WASM module manages focus, text buffer, and cursor — the JS only forwards events

### 5.6 Missing: `.alk` Source File and Compilation Path

**Status:** No `.alk` file exists. The scene is constructed directly in Rust.

**Evidence:**
- The `alkalive-app/src/lib.rs` hard-codes `HELLO_WORLD_TEXT = "Hello World!"` and constructs the `TextScene` in the `init()` function
- There is no parser, no AST, no IR — the scene structure is implicit in the Rust code

**What's needed:**
1. Define the `.alk` language grammar (module, scene, text node, input field)
2. Write a `hello.alk` file that declares the scene
3. Compile it to a scene IR that the runtime can consume
4. The runtime reads the IR and constructs the scene at startup

## 7. Conclusion

The deployed "Hello World" is a **mock/simulation** of an AlkALive application, not a real one. It uses:
- **CPU software rendering** instead of WebGPU
- **JavaScript frame loop** instead of WASM-owned rendering
- **React/DOM/CSS UI** instead of AlkALive-rendered UI
- **Hard-coded Rust scene construction** instead of compiled `.alk` source

The root cause is that **6 critical infrastructure pieces are missing** (G1–G6): the compiler, the WebGPU backend, the render loop, the compositor, the runtime wiring, and the JS-owned frame loop. Without these, the previous agent had no choice but to fall back to traditional web technologies.

The fix requires building the missing compiler and runtime infrastructure so that a `.alk` source file can be compiled into a WASM binary that owns the entire rendering pipeline via WebGPU, with only a minimal HTML shell for canvas hosting.
