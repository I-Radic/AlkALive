# Rough Draft — Architectural Response to the Problem Catalog

**A design-rationale draft for a custom, module- and object-oriented language compiling to WebAssembly with direct WebGPU rendering.**

This draft is derived from `docs/PROBLEM_CATALOG.md` (the 50-reference literature review) via a four-wave sub-agent validation campaign: draft construction, internal consistency check, pairwise cross-area integration, and evidence traceability. Each cluster below follows the four-part structure **Problem / Goal / Solution / Integration**. Problem statements are grounded in the catalog's problem-entry IDs (`P x.y`) and references (`[n]`); claims resting on circumstantial evidence or catalog-acknowledged literature gaps are marked *`(inferred)`* or *`(catalog gap G n)`*.

---

## 1. Rendering Pipeline & Compositing

**Problem.** The browser's retained-mode, box-model pipeline (style recalc → layout → paint → composite) is optimized for documents and structurally resists application use `[32]`. The box is the atomic render unit; no first-class vertex, textured polygon, or GPU draw call is exposed to authors, and the layered stages cannot be bypassed or reordered for batching `[33]`; the compositor is shared and observable across origins `[34]` (P1.1). Stacking contexts, compositor layers, and paint order are governed by implicit CSS rules, and layer promotion is engine-heuristic-dependent *(inferred from engine internals; the catalog asserts this without a dedicated citation)* (P1.2). A single DOM mutation can invalidate an arbitrarily large subtree because layout is a global constraint solver over the box tree `[33]`, with reflow/repaint classed as a recurring real-world performance bug `[20,21]` (P1.3). Selector matching is a measured pipeline bottleneck `[33]`; *(catalog gap G2: direct CSSOM-construction-cost measurement is sparse, so the "dominant frame cost" framing for CSSOM rebuild specifically is partly inferred)* (P1.4). The DOM/CSSOM/render-tree trinity forces all visual output through one document-shaped tree, preventing independent scene graphs from sharing a compositor on equal terms `[32,34]` (P1.5).

**Goal.** An ideal WASM-compiled, WebGPU-rendered language should make the GPU draw call — not the box — the atomic unit; expose the render graph, pass ordering, draw-call batching, occlusion culling, and layer promotion as author-owned, contractual primitives; replace global reflow with locally-scoped invalidation; eliminate selector matching and the cascade; and permit multiple independent scene graphs composed by explicit GPU passes.

**Solution.** The language exposes a render-graph IR as a first-class object whose nodes are passes, attachments, draw calls, and an explicit occlusion-culling pass — not boxes. Each UI module owns a scene graph and its invalidation model (dirty rectangles, per-object layout), so a mutation recomputes only the affected subgraph; this *requires a layout-locality guarantee* from the new solver (no cross-module percentage/flex dependencies that would re-introduce global reflow). Styling is expressed as compiled object properties on scene nodes — no cascade, no selector matching — folding P1.4's selector-matching cost to zero. The compositor becomes an explicit GPU pass scheduler: the author declares layer promotion, geometry batching, and occlusion rather than relying on heuristics. Draw-call ownership resides with the author, allowing custom shader passes between stages and free reordering for batching. Multiple render graphs (3D viewport, HUD, text layer) register with a shared compositor service that serializes all submissions through a single render thread owning the `GPUDevice` — a concurrency model that requires `SharedArrayBuffer` under COOP/COEP cross-origin isolation.

**Integration.** Layout/styling is the single source of truth: per-instance WASM property state plus a pluggable constraint solver (box solver + mandatory text-flow sub-solver) own all property and layout computation; text-flow results feed back into the box solver, then into the render graph, closing the "text outside box model" gap (§2, §3). Solver outputs upload directly as GPU transforms and drive dirty-rect invalidation with layout-locality guarantees; the GPU-resident, solver-internal layout-tree supersedes any duplicate "compiled object properties" phrasing (§2). The render-object tree (§3) is the single source feeding this render-graph IR; culling splits cleanly — scene-level instance/cull in the tree, occlusion-cull as a render-graph pass. Abandoning the DOM threatens accessibility, input, and text semantics (P3.5, P5.1, P6.1), so the scene graph emits a parallel semantic tree (the virtual accessibility tree of §6) via a host service — not the render graph itself, which is GPU-pass-level. Explicit batching and local invalidation directly target the reflow/repaint and style-recalc bug classes `[20,21]` (§7). Cross-engine selector divergence (P2.4) is mooted, but GPU-backend portability must be independently verified.

## 2. Layout & Styling

**Problem.** CSS exhibits five interlocking limitations (P2.1–P2.5). Styling is global and cascading with a triadic specificity comparator that produces non-local, hard-to-predict side effects; BEM, CSS Modules, CSS-in-JS, and Shadow DOM are after-the-fact confinement workarounds on a model with no built-in scope *(catalog gap G1: no widely-cited peer-reviewed metric study of cascade-maintainability cost; support is circumstantial via cross-browser divergence `[30]` and the proliferation of scoping methodologies)* (P2.1). Stylesheets are parsed into a CSSOM at load and on every change with no compact binary representation; selector matching is a pipeline bottleneck `[33]` *(the "measured startup bottleneck" framing overstates [33], which supports selector matching as a stage, not direct startup-cost measurement — G2)* (P2.2). Flexbox/Grid are constraint solvers over rectangular boxes only — they cannot express physics-based, non-rectangular, or directed-graph layouts, and the constraint vocabulary is fixed and engine-internal `[33]`; cross-browser divergence in flexbox/grid resolution `[30]` shows the semantics are unstable (P2.3). Identical HTML/CSS renders differently across browsers because cascade, defaults, and layout-solver semantics are not interoperable; WEBDIFF found widespread visual divergence `[30]`, and Visual Web Test Repair exists because DOM/CSS tests break across engines and over time `[31]` (P2.4). CSS offers only a closed catalogue of engine-defined effects; authors cannot supply shader gradients, per-vertex transforms, particle effects, or compute-shader-driven styling, and the styling layer sits above and apart from the GPU pipeline `[35]` (P2.5).

**Goal.** An ideal alternative must make styling scoped, object-owned state rather than a global cascade; ship it as compiled binary state with no runtime CSSOM or selector matching; support arbitrary user-defined constraint solvers over first-class objects (springs, collisions, non-rectangular regions, graph layouts); guarantee single-renderer determinism so the author's module *is* the layout engine; and unify styling with shading so any element can be driven by author-supplied WGSL shaders and compute passes.

**Solution.** Styling becomes per-instance object property state — color, transform, effect — bound at construction and addressable only through the owning object, eliminating the cascade and specificity entirely. A compiled WASM module carries this state in a compact binary form, removing the CSSOM parse/match stage. Layout is delegated to an explicit, pluggable constraint solver operating over first-class objects — Cassowary-style linear, impulse-based physics, or graph-layout — whose results feed GPU transforms directly. **A mandatory text-flow sub-solver (Knuth-Plass line-breaking and HarfBuzz-backed shaping) is a built-in, not optional**, since the box/physics/graph solvers cover none of line-breaking, BiDi reordering, or font-metric shaping — the hardest layout problem. Crucially, there is *no style-driven box-tree recalc*; the layout-tree is solver-internal and GPU-resident where possible (positioned nodes use direct GPU transforms, but text layout, overflow clipping, scroll containers, and hit-testing retain hierarchical intermediate state). Visual effects become WGSL shader programs bound to object instances; the renderer exposes WGSL entry points and compute passes as first-class styling primitives, so gradients, particles, and per-vertex transforms are authored rather than approximated by a fixed `filter` catalogue.

**Integration.** With the Rendering Pipeline (§1), solver outputs become direct GPU transform uploads with no style-driven box-tree recalc `[33,34]`; WGSL instance effects are scheduled as explicit compositor passes. With Composition (§3), scoped object-owned styles remove the reconciliation layer between component and style trees. With Text (§3, P3.5), the text-flow sub-solver supports inline-run flow layout and feeds the text stack's measurement stage. With Performance (§7), binary-shipped state and GPU-resident effects cut first-paint cost and enable per-frame shader-driven styling without DOM jank. The layout-locality guarantee required by §1's local invalidation is a property this solver must enforce.

## 3. Document Model & Composition

**Problem.** HTML and the DOM are document-shaped primitives forced into application use. The document substrate resists application-platform repurposing `[32]`, producing "div soup" where semantic HTML conflicts with custom UI (P3.1). Every modern framework (React, Vue, Angular, Web Components) maintains its own component tree reconciled *into* the DOM's box tree — a permanent impedance mismatch evidenced by cross-browser test-repair `[30,31]`, AJAX-state-crawling `[27,28,29]`, and brittle DOM-coupled JavaScript `[25,26]` (P3.2). Style recalc, layout, and paint scale super-linearly with tree size, driving the universal "do not exceed N nodes" rule and making 120 fps unattainable for large UIs `[20,21,33,34]` (P3.3). The imperative mutation API (`appendChild`, `innerHTML`, attribute setters) is globally observable and lifecycle-fragile, with DOM/event/state interactions dominating real bug taxonomies `[22,23,24]` (P3.4). **P3.5 — text rendering locked to the DOM — is the decisive hard problem:** shaping, BiDi, line breaking, selection, caret, IME, and accessibility are contractual only on DOM text nodes; canvas `fillText` provides none, and even data-visualisation labels rendered outside the DOM lose screen-reader access `[39,40,41]`. The catalog flags P3.5 as the strongest lock-in in the entire architecture and the problem most likely to determine viability (§11, §12).

**Goal.** An application-oriented object tree that replaces document elements with first-class application primitives (panels, canvases, glyphs, splines); a single tree owned by the module with no reconciler, no hydration, no SSR/CSR divergence; a GPU-resident scene graph whose cost profile is independent of "DOM node count"; explicit object lifecycles under module control; and — mandatorily — a first-class text stack that makes text a peer of geometry rather than a DOM-locked substrate.

**Solution.** One owned render-object tree in which module objects *are* the render objects (Flutter-style), eliminating the reconciliation layer of P3.2 and the imperative mutation surface of P3.4 at once. Construction/destruction is module-controlled, replacing P3.4's global observability with explicit state transitions. The scene graph is GPU-resident with instancing and culling, decoupling paint cost from tree size (P3.3); layout cost is bounded by retained/incremental dirty-region layout. On this tree, a mandatory first-class text stack is built — shaping (HarfBuzz/WASM or bespoke), BiDi, measurement, line breaking, selection, caret, IME — with **only IME and accessibility contracts routing to the platform via a thin bridge (a hidden input element for composition events, a virtual accessibility tree for a11y)**, *not* a DOM render path; shaping, BiDi, and selection live entirely in WASM. The architecture is single-source, multiple-emission-targets: the render-object graph is the one source, emitting to WebGPU render, the virtual accessibility tree, and the IME bridge.

**Integration.** The render-object tree is the single integration surface — but "single source, multiple emission targets," not a single output. **Rendering** (§1) consumes it directly as WebGPU draw calls via the render-graph IR. **Layout** (§2) becomes a stage over owned render objects with font resolution from the text stack woven in `[33]`. **Accessibility** (§6, P6.1) is emitted as a virtual tree derived *from the same objects* — the catalog's co-decisive hard problem alongside P3.5; the a11y module owns the tree derivation, the text stack produces the shaping/BiDi/selection/caret/label data that the a11y tree consumes. **Interaction** (§5) hits owned hit-testing rather than DOM event dispatch. The text stack is the most heavily depended-upon component: layout's measure stage, accessibility's textual exposure, selection/IME interaction, and the P3.5/P6.1 viability gate all rest on it. *(WASM+GPU feasibility is sound: HarfBuzz/ICU/BiDi are proven in WASM; GPU scene graphs are proven; the only bridge to platform is IME composition + the a11y virtual tree.)*

## 4. Language Design & Component Model

**Problem.** JavaScript's runtime semantics force a class of bugs and compensating toolchains that a target language need not inherit. (i) **Dynamic typing** makes type errors runtime phenomena; TypeScript adds optional static types without changing the runtime, and a large PL literature has been spent retrofitting inference `[9,10,15]`, type systems `[11,12,14]`, dependent `[12]` and recency `[14]` types, and DOM-aware analyses `[15,16]` onto a language that lacks them. Gao, Bird & Barr estimate static typing would have caught ~15% of real bugs `[19]`; BugsJS catalogues hundreds of type-shaped defects `[22]`; Richards et al. document how pervasively programs rely on dynamic features that defeat static reasoning `[7]` (P4.1). (ii) The **prototype object model**, `this`-binding, and late private fields frustrate encapsulation; the repeated need for language-based isolators (Maffeis & Taly `[17]`, ConScript `[18]`) evidences that native boundaries are absent (P4.2). (iii) The **callback/Promise/timer** substrate produces structural async bugs empirically characterised by Gallaba et al. `[23]` and Ocariza et al. `[24]`, with timer semantics so underspecified they are a security hazard `[48,50]` (P4.3). (iv) **JIT warmup and deoptimisation cliffs** yield engine-heuristic-dependent performance `[13,20,21]`; WASM was designed to be predictably AOT-compilable `[1,2,4,6]` (P4.4). (v) Modern component models still inherit the box model and the HTML/CSS/JS trinity; the DOM's externally-observable state is not owned by any component `[27,28,29,30,31]`, and Shadow DOM scopes style but not the rendering model (P4.5). (vi) ES modules give code modularity but no **language-level UI modularity**; structure, style, behaviour, and rendering cannot be bundled into one separately-compilable, verifiable unit, so each concern is bolted on `[9,10,11,12,14,15,16,17,18]` *(catalog uses range `[9-18]`; the precise set omits [13], which belongs only to P4.4)*, in contrast to the mechanised, verifiable module boundary WASM offers `[3,5]` (P4.6).

**Goal.** The ideal alternative language should (a) carry a sound static type system that compiles down to WASM's *validated* type system, turning type errors into compile-time errors; (b) provide first-class modules and encapsulation as a language primitive, not a convention; (c) *choose a single coherent concurrency/scheduling model* rather than inheriting the browser event loop; (d) make the UI component a language-level unit bundling structure, style, behaviour, and rendering; (e) yield predictable AOT performance; and (f) yield verifiable, separately-compilable module boundaries.

**Solution.** A statically-typed, module- and object-oriented language compiling to WASM, with first-class UI modules: each component *is* a render-object subtree owning its styling, layout, and drawing — an explicit architectural commitment that **abandons DOM/HTML/CSS as the rendering substrate** (not a hidden consequence). Explicit ownership and visibility replace closures/Symbols/WeakMaps (P4.2). The module owns **one unified scheduler** — cooperative coroutines integrated with a retain-mode render loop — rather than offering a disjunctive menu of concurrency options; this single scheduler drives layout, rendering, accessibility-tree emission, and IME bridging each tick. Static types map to WASM's validated types as a **two-level guarantee**: the compiler proves source-level soundness, and WASM verifies compiled well-formedness — *not* a claim of end-to-end semantic verification, since WASM validation is structural rather than a soundness proof.

**Integration.** **Composition (§3, §5):** language-level components compose as render-object subtrees, removing DOM/box-model impedance and unifying hit-testing and input dispatch; the unified scheduler drives §3's pipeline stages (font-resolved layout, WebGPU rendering, virtual a11y-tree emission, IME bridging), each tick producing dirty-region invalidation. **Performance (§7, P4.4):** the WASM target replaces JIT heuristics with a predictable AOT ceiling `[1,2,6]`. **Tooling/HMR (§8):** first-class modules give precise replacement units for hot reload; HMR replaces a component subtree as a single invalidation unit, re-entering the scheduler. **Bundle (§9):** separately-compilable modules reduce framework-coupled reuse; the Language cluster owns the typed-import, module-boundary, and host-DOM interop *interface contract* that §6/§3 implement bridges against. **Accessibility (§6):** owned render objects expose a stable semantic contract. **WASM verification interplay:** static types + WASM's mechanised, validated module boundaries `[3,5]` make encapsulation and type soundness jointly verifiable — though only at the structural/well-formedness level.

## 5. Interaction & Input

**Problem.** The DOM event model (capture → target → bubble) is structurally bound to the DOM tree, so when UI elements are virtual — drawn on canvas or represented by a sparse subtree — hit-testing must be reimplemented and synthetic events fail to compose with native focus/pointer contracts (P5.1). Pointer Events unify mouse/touch/pen at the DOM level, but stylus pressure/tilt, multi-touch gestures, and gamepad remain awkwardly surfaced and engine-dependent, because the input vocabulary is tied to the DOM element under the pointer rather than the drawn primitive or the logical tool *(catalog gap G6: direct peer-reviewed measurement of input-pipeline overhead for virtual/drawn elements is sparse; P5.2 rests partly on structural evidence)* (P5.2). Focus, tab order, and the focus ring are DOM-tree properties, so a canvas-drawn UI has no native focus model and must fabricate one that assistive technology cannot reliably observe (P5.3). DOM-event-coupled JavaScript behaviour is fragile under change `[25,26]`; AJAX-state-inference work shows the system must *infer* which UI state an event corresponds to `[27,28,29]`; the screen-reader studies confirm that virtual elements are undefined to assistive tech `[39,40,41]`.

**Goal.** The ideal alternative should make hit-testing a first-class property of render objects themselves; treat pointer, multi-touch, stylus, and gamepad as uniformly first-class device-event streams dispatched directly to the hit render object; and provide a virtual focus and tab-order model that is not bound to any DOM, yet remains observable by platform accessibility APIs.

**Solution.** The WASM module owns hit-testing against a **CPU-resident bounding-volume mirror** of the GPU scene (or, for precise picks, a per-query GPU pick-buffer readback); the GPU scene geometry remains the source of truth, but WASM cannot query GPU-resident buffers directly, so a queryable primitive-bounds mirror is mandatory. A first-class input model receives raw device state and dispatches device events (pointer/stylus/multi-touch/gamepad) to render objects, which implement their own gesture/state machines. A virtual focus/order model tracks the active render object and tab sequence independently of any host document tree. **This focus model is co-owned with §6/P6.1:** the focus tree and the accessibility tree are *one structure* — a derived view of the render-object graph — and input dispatch is the sole writer of focus state while accessibility is the reader/announcer.

**Integration.** Tightly coupled to the Rendering Pipeline (§1): hit-testing consumes the same scene geometry the renderer produces, so the GPU scene must expose queryable primitive bounds (the CPU mirror). Critically, the virtual focus/order model is **shared with** Accessibility (P6.1): focus, tab order, and the focus ring become properties of the virtual accessibility tree rather than a DOM contract, so the object receiving input is the same object announced to assistive technology. This bidirectional hard dependency is the central §5↔§6 contract: input dispatch is the sole writer of focus state; a11y is the reader; activation contracts (gesture → focus move → a11y live-region update) flow back as a11y state changes. Capability-scoped imports (§9) gate both interactive semantics and input dispatch. This eliminates the DOM/canvas split documented in `[39,40,41]` and prevents the WASM+GPU stack from reproducing the canvas accessibility blackout.

## 6. Accessibility & Platform Integration

**Problem.** The web's accessibility architecture — ARIA roles, the accessibility tree, focus, screen-reader events — is contractually bound to the DOM tree (P6.1). When output is rendered imperatively on a canvas, assistive technology loses every affordance: there is no DOM node to describe, focus, or navigate. Sharif, Chintalapati, Wobbrock & Reinecke's study documents the *systemic* inaccessibility of DOM-light visual content `[39]`; VoxLens `[40]` and "Rich Screen Reader Experiences" `[41]` exist precisely because the default DOM/canvas split leaves visualisations inaccessible; Ara, Sik-Lányi & Kelemen's review confirms accessibility is routinely an evaluation-driven retrofit, not a first-class platform property `[42]`. **P6.1 is decisive**: the catalog ranks it the second-hardest problem after text (P3.5). P6.2: the URL/history model assumes addressable document states, so canvas apps must fabricate lossy navigation mappings `[27,28,29]` *(catalog gap G5: direct canvas-navigation studies are sparse; evidence is indirect via AJAX-state inference)*. P6.3: SEO depends on DOM-present content; pure-canvas apps are invisible or degraded to crawlers, structurally ceiling the vision's applicability `[27,28,29]`. P6.4: even *with* a DOM, rich visualisations lack mature accessibility tooling — sonification, structured query, multimodal output remain research artefacts `[40,41,42]`.

**Goal.** The ideal alternative treats accessibility as a first-class platform contract, not a retrofit. Every render object declares a semantic role, structured data, and interaction affordance. The module emits a *virtual accessibility tree* to platform accessibility APIs (the same bridges browsers use), giving assistive technology contractual access to GPU-drawn UI. App-like interfaces gain a structured navigation/state contract addressable by URL and history. SEO is scoped with an *explicit scope declaration*: app UIs declare a non-SEO domain; public/document content ships a hybrid or structured-content export path.

**Solution.** (1) Every render object carries semantic role + structured data + interaction descriptor as mandatory fields, not optional attributes. (2) The module **derives** a virtual accessibility-tree *view* from the render-object graph (not a separately authored mirror), bridged to platform accessibility APIs rather than to a DOM mirror. (3) A structured navigation/state contract exposes application routes and serialisable state to the host explicitly, replacing fabricated URL mappings. (4) Accessibility becomes a compile-time-checkable property: missing roles, unreachable focus targets, or unlabelled interactive objects surface as type/lint errors, not runtime omissions — directly answering P6.4's tooling gap.

**Integration.** Co-equal hardest with Text (P3.5): the catalog treats P6.1 and P3.5 as the two decisive design problems, and §3's "text stack most heavily depended-upon" framing yields to this co-equal priority. With **Interaction** (§5): the focus model is shared — focus, tab order, and the focus ring become properties of the virtual accessibility tree; input dispatch (§5) is the sole writer of focus state, a11y is the reader. With **Rendering Pipeline** (§1–§3): render objects carry semantics natively, so the accessibility tree is derived from the same object graph that drives WebGPU draw calls — no separate mirror to keep in sync; each layout commit mirrors to the parallel semantic tree. With **Text** (P3.5): textual labels, selection, and caret state produced by the text stack flow through the same semantic declarations, ensuring canvas-rendered text is accessible; IME composition routes through the text stack's thin platform bridge and reflects into the tree. With **Modules** (§9): capability-scoped imports gate which objects may declare interactive semantics, reducing retrofit risk; §6's derived virtual a11y-tree and structured navigation/state are the mandatory payloads crossing §9's host-DOM interop bridges.

## 7. Performance & Runtime

**Problem.** The DOM-based runtime cannot deliver predictable high frame rates or fine-grained parallelism, and the WASM escape hatch is structurally neutered by the interop boundary. P7.1: sustained 60 fps — and especially 120/144 fps — is unreliable in large DOM applications because layout, paint, and compositing costs are super-linear and shared across the document; Meyerovich & Bodik parallelised layout because it was a measured sequential bottleneck `[33]`, Wu et al. show the compositor is shared and contention-prone `[34]`, and Sengupta et al. document that browser GPU acceleration is uneven and that the DOM styling/compositing layer sits apart from the raw GPU pipeline `[35]`. P7.2: the main thread is single-threaded and owns the DOM; Web Workers cannot touch the DOM and incur structured-clone/serialization overhead per interaction, so off-main-thread UI work is rarely worth its cost `[33]` *(catalog gap G4: direct fine-grained measurement of serialization-induced UI jank is thin; the contract is well-established but the bottleneck magnitude is partly inferred)*. P7.3: Selakovic & Pradel's empirical studies `[20,21]` (with related correctness evidence in `[22,23,24]`) show DOM/layout-coupled performance bugs are a dominant, recurring category. P7.4: WASM runs at ~1.5× slower than native for self-contained computation `[2]`, but the WASM↔JS/DOM boundary adds per-call overhead; Hilbig et al.'s study of real-world WASM binaries `[6]` finds usage is coarse-grained (codecs, crypto), not fine-grained UI — direct evidence that interop overhead steers usage away from the hot path.

**Goal.** Make 60/120 fps predictable and governed purely by draw calls and fill rate, independent of DOM-tree size; provide off-main-thread parallelism with the GPU scene as shared state and zero serialization; **eliminate the DOM/layout-coupled performance-bug class** (P7.3, promoted from a side-effect to an explicit goal); and eliminate the WASM↔DOM interop boundary in the hot path so WASM's compute advantage actually reaches the UI.

**Solution.** A GPU-resident, WASM-driven render loop whose cost is governed by draw calls and fill rate rather than tree size, using explicit dirty rectangles and per-object layout to bound per-frame work. Parallelism comes from WASM threads over `SharedArrayBuffer`, with **scene-graph data living in the SharedArrayBuffer and a single render thread owning the `GPUDevice`** (WebGPU `GPUDevice`/objects are agent-bound, not freely shareable across workers — so the model is: shared scene data in SAB, one device-owning render thread). This requires COOP/COEP cross-origin isolation headers, a deployment constraint that may conflict with third-party iframe embedding. The UI itself is compiled to WASM, so the WASM↔DOM boundary does not exist in the hot path: the same module that computes layout issues WebGPU draw calls directly.

**Integration.** *Rendering Pipeline* (§1): replaces the shared super-linear layout/paint/composite path `[33,34,35]` with an author-owned GPU render loop; the "new solver" of §1 *is* the WASM layout engine, and multiple render graphs register with the shared compositor that serializes all submissions through the single device-owning render thread. *Layout* (§2): per-object, dirty-rectangle-driven layout supersedes the shared reflow/repaint cycle that dominates the bug catalog `[20,21]`. *Bundle/Startup* (§9): the WASM module is itself the layout engine, so start-up is *one streaming-compiled module load* (not an engine+framework+app stack); WebGPU pipeline precompilation eliminates the GPU-side startup floor. *Language concurrency* (§4): the unified scheduler integrates with WASM threads + SharedArrayBuffer to replace Web-Worker serialization. The "no interop boundary" claim is **conditional** — it depends on the Composition (§3) and Document-Model clusters providing a scene-graph/object model that lives entirely inside WASM, with no DOM fallback in the hot path; a11y, input, and out-of-box-model text remain open dependencies requiring dedicated services (§3, §5, §6).

## 8. Tooling & Developer Experience

**Problem.** The web's tooling layer is fragmented across four documented failure modes. P8.1 identifies a *design-tool-to-runtime gap*: design tools (Figma, Sketch) approximate but cannot reproduce the live runtime layout interpreter `[33]`, and cross-browser divergence `[30]` means there is no single runtime to replicate; "design-to-code" handoff is therefore lossy. P8.2 documents *HMR fragility*: because the DOM is one mutable tree coupling view, style, and behaviour, surgical code replacement rarely preserves runtime state, and style changes cascade unpredictably *(inferred: no HMR-specific peer-reviewed evidence in the catalog; the claim is an inference from mutation-testing brittleness `[25,26]` and test-repair `[30,31]`, which the catalog concedes are "downstream symptoms of the same coupling")* (P8.2). P8.3 exposes *DevTools opacity*: JS, performance, rendering-layer, and DOM panels are only coarsely observable, so the causal link between a JS change and a layout/paint/composite cost requires expert inference *(inferred: the catalog uses the need to empirically study perf bugs `[20]` and auto-fix them `[21]` as indirect evidence that causes are not legible — no direct DevTools-observation study is cited)* (P8.3). P8.4 records *test fragility*: DOM/CSS end-to-end tests break on selector drift, layout shifts, and cross-engine differences, spawning Visual Web Test Repair `[31]`, WEBDIFF `[30]`, and BugsJS `[22]`.

**Goal.** The ideal alternative collapses the design/runtime boundary so the design tool *is* the runtime engine; makes hot reload reliable and state-preserving; renders a single causal trace spanning logic, layout, and draw; and supports non-brittle component-level testing of rendering and interaction.

**Solution.** A deterministic, author-owned renderer (a WASM module that *is* the layout engine) is embedded *into* the design tool, so design and runtime are literally the same engine — pixel-perfect fidelity by construction rather than approximation. UI state lives in an owned, serialisable scene graph; on hot reload the module's state is treated as data and rehydrated into a freshly loaded module, decoupling code replacement from state preservation. Because the author owns logic, layout, and draw, a single author-owned trace spans all three pipeline stages, making frame drops root-causable in one view. Typed component contracts replace DOM-selector queries, enabling component-level testing without selector or cross-engine brittleness.

**Integration.** HMR state preservation relies on the Language/Component Model (§4) to expose owned, serialisable scene-graph state — §4 provides the HMR replacement unit (first-class module) and §8 provides the preservation mechanism (state rehydration); the round-trip (replace module → rehydrate state) is the shared contract, and §4's "serialisable render-object subtree" and §8's "serialisable scene graph" denote the same artifact (terminology unified). The unified trace depends on Rendering+Layout being deterministic and author-owned — **split into two parts**: *layout determinism is guaranteed by the WASM sandbox*, while *rendering determinism requires a deterministic GPU compute path or a software-rasteriser fallback* for trace correlation (GPU rasterisation is not guaranteed cross-vendor deterministic). If rendering is non-deterministic the trace cannot correlate cause to cost, and the design-tool-as-runtime guarantee of P8.1 likewise collapses — so §8's design-tool promise is downstream of a deterministic rendering path. The unified trace also implicitly depends on §4's single unified scheduler; any scheduler nondeterminism would silently break trace correlation. Component test contracts are expressed through the Composition model (§3): typed inputs/outputs and explicit child slots replace selector-based assertions, integrating with the same contracts that govern composition and reuse.

## 9. Bundle, Startup & Ecosystem Lock-in

**Problem.** The HTML/CSS/JS trinity ships as text parsed at runtime, so large bundles impose a parse/compile startup floor that code-splitting, tree-shaking, and critical-CSS only fight, never remove (P9.1) `[1,6,20,21,33,34]`. The npm supply chain nearly every frontend depends on is a structural security liability: Ohm et al. review 174 malicious open-source packages, the majority in npm (P9.2) `[43]`. The same ecosystem exhibits dependency bloat — Liu et al. detect bloated dependencies in JavaScript/CommonJS packages `[44]`, and Decan et al. show npm's dependency network is among the densest and fastest-evolving of seven ecosystems, amplifying bloat and churn (P9.3) `[45]`. Framework churn (jQuery → Angular → React → Vue → Svelte → …) imposes near-total switching costs on components, tooling, hiring, and tests (P9.4) `[30,31,46]`. Meyerovich & Rabkin's adoption study `[46]` shows ecosystem inertia — not technical merit — dominates language/platform adoption, making the alternative's adoption the central non-technical risk (P9.5); technically superior stacks (Elm, Reason) have struggled for exactly this reason.

**Goal.** The ideal alternative must: (a) set a compact WASM binary startup floor governed by module decode, not three-language text parsing; (b) reduce the dependency and supply-chain surface to a verified, language-level standard library; (c) enforce capability-scoped imports replacing npm's transitive trust with least-privilege grants; (d) provide a stable, verifiable module boundary `[3,5]` that decouples components from framework churn — components become modules, not framework artifacts; and (e) chart a credible adoption path despite ecosystem inertia, since technical superiority alone is insufficient `[46]`.

**Solution.** A compiled WASM UI module ships a compact, fast-to-decode binary `[1,6]` whose startup is bounded by decode (and WebGPU pipeline precompilation eliminates the GPU-side startup floor), not HTML/CSS/JS parsing. A language-level standard library shrinks the transitive dependency surface that bloats bundles and exposes attack surface `[43,44,45]`. Explicit, typed imports with compile-time tree-shaking make unused-dependency elimination a guarantee — *component-model-enforced, with a maturity note* (the guarantee's strength tracks WASM component-model maturity) — rather than a tooling hope (P9.3). Capability-based, sandboxed imports bound each dependency's authority, replacing transitive trust with least-privilege grants (P9.2). A verifiable module boundary `[3,5]` makes components modules, not framework artifacts, isolating them from churn (P9.4). Host-DOM interop bridges — for text, accessibility, and navigation where the DOM is mandatory (§11) — enable incremental adoption so the new stack coexists with the incumbent rather than requiring a multi-year rewrite.

**Integration.** The **Language** cluster (§4) owns the typed-import, module-boundary, and host-DOM interop *interface contract* — including the contract that §6/§3 implement bridges against; the boundary between contract-definer (Language) and bridge-implementer (A11y/Text) is explicit. The **Performance** cluster (§7) owns the WASM decode/startup floor and WebGPU pipeline precompilation. The **Accessibility/Text** clusters (§6, §3) own the host-DOM interop bridges that P9.5 makes strategically mandatory: §6's derived virtual a11y-tree and structured navigation/state are the mandatory payloads crossing §9's interop bridges — the "what" (a11y tree, nav state) vs. "mechanism" (the bridge) link is now stated; interop is the adoption gateway, not an optional convenience. Critically, P9.5 adoption risk is *strategic* (§11) and gates the entire effort — technical correctness on §1–§8 is insufficient unless ecosystem inertia is addressed first-class through incremental interop and a credible standard library `[46]`.

## Integration Overview — A Cohesive Architectural Vision

The nine cluster solutions resolve into a single coherent architecture organised around one principle: **the render-object tree is the single source of truth, owned by the WASM module, with multiple emission targets.**

**The spine.** A statically-typed, module- and object-oriented language (§4) compiles to WebAssembly. Each UI component *is* a render-object subtree (§3), explicitly abandoning DOM/HTML/CSS as the rendering substrate. The module owns one unified scheduler (cooperative coroutines + retain-mode loop) that drives, each tick: font-resolved layout (§2, §3), WebGPU rendering via an explicit render-graph IR (§1), virtual accessibility-tree emission (§6), and IME bridging (§3). Layout commits produce dirty-region invalidation bounded by a layout-locality guarantee (§1, §2). The scene graph is GPU-resident with scene data in a `SharedArrayBuffer` and a single render thread owning the `GPUDevice` (§7), under COOP/COEP isolation.

**The two decisive hard problems.** Text (§3, P3.5) and accessibility (§6, P6.1) are co-equal hardest and determine viability. Both are solved by making the render-object tree the substrate: the text stack (shaping/BiDi/measure/selection/caret/IME) lives in WASM, with only IME composition and the a11y virtual tree crossing to platform via thin bridges; the a11y module *derives* (not authors) a virtual a11y-tree view from the same object graph that drives WebGPU draws, so there is no separate mirror to keep in sync. The focus model (§5) is one with the a11y tree: input dispatch is the sole writer of focus state, a11y is the reader/announcer — eliminating the DOM/canvas accessibility blackout `[39,40,41]`.

**Cross-cutting services.** Layout is a pluggable constraint solver (box + mandatory text-flow sub-solver) whose outputs are direct GPU transforms (§2). Styling is per-instance object property state, compiled to binary, with WGSL effects as first-class primitives (§1, §2). Hit-testing runs against a CPU-resident bounding-volume mirror of the GPU scene (§5). Interactivity, accessibility semantics, and input dispatch are all gated by capability-scoped imports (§9).

**The feedback loops.** Tooling (§8) embeds the deterministic author-owned renderer *into* the design tool (same engine → pixel-perfect); HMR replaces a component subtree as one invalidation unit with state rehydrated from the serialisable scene graph (§4 + §8); a single author-owned trace spans logic+layout+draw, with layout determinism guaranteed by the WASM sandbox and rendering determinism requiring a deterministic GPU path or software-rasteriser fallback. Bundle/startup (§9) collapse to one streaming-compiled WASM module plus WebGPU pipeline precompilation, with a language-level standard library and capability-sandboxed, tree-shaken imports shrinking the supply-chain surface.

**The strategic gate.** All of the above is technically necessary but insufficient on its own: Meyerovich & Rabkin `[46]` show ecosystem inertia — not technical merit — dominates adoption. The host-DOM interop bridges (for text, a11y, and navigation) are therefore not optional conveniences but the **adoption gateway**, enabling incremental coexistence with the incumbent web stack. The Language cluster owns the interop *interface contract*; the A11y and Text clusters implement the bridges; their payloads (virtual a11y tree, structured navigation state) cross that contract. Without this incremental path, the alternative reproduces the adoption failure of Elm and Reason regardless of its technical superiority.

**Resolved cross-area conflicts.** Single-source ownership of the render-object tree (not §1's "multiple scene graphs" vs §3's "one tree" — resolved: one tree feeds multiple render graphs registered with the compositor). Single focus/a11y structure (not §5's "one structure" vs §6's "derived view" — resolved: one derived view, input writes, a11y reads). Unified scheduler ownership (§4 owns it; drives §3's stages). Interop interface ownership (§9 defines; §6/§3 implement). Terminology unified ("serialisable render-object subtree" = "serialisable scene graph"). Culling split (scene-level instance/cull in the tree; occlusion-cull as a render-graph pass).

**Open risks.** GPU-backend portability and cross-vendor rendering determinism (§1, §8); WASM component-model maturity for guaranteed tree-shaking (§9); COOP/COEP deployment constraints vs third-party iframe embedding (§7); and the catalog-acknowledged literature gaps (G1 cascade-maintainability metrics, G2 CSSOM-construction cost, G4 Worker-serialization magnitude, G5 canvas-navigation, G6 input-pipeline overhead) — each flagged inline where the corresponding Problem claim rests on circumstantial rather than direct peer-reviewed evidence.
